# dsh-sift v0.2 实施文档

> 历史实施方案：本文记录 v0.2 当时的实施拆分，不代表所有阶段均已完成。当前状态以 [`路线图.md`](../路线图.md) 和 [`使用流程.md`](../使用流程.md) 为准。

本文件是 [v0.2 设计方案](v0.2-设计方案.md) 的落地版。设计与实施各自独立编号。

## 1. 实施目标

v0.2 的目标不是继续修补旧的 Material / Project / Solution 体系，而是重新建立一条清晰、可运行、可逐步验证的主链：

```text
Source → Reference → Session → Document
```

对应到实现：

```text
SourceResolver / Source Tools → Reference Board → ReferenceCodec
   → DSH Session → DocumentChangeTool → Document Diff
```

只要这条链顺畅，v0.2 就成立。

## 2. 实施原则

### 2.1 新模型优先

旧代码只能按“能力”复用，不能为了复用旧代码继续保留旧抽象。以下概念退出 v0.2 主链：Solution、Project、Material Workspace、旧 Annotation 体系、旧素材组织逻辑。如果旧模块不能明确映射到 Source / Reference / Document / Session，优先删除。

### 2.2 不过度设计权限

Source 是否位于 Workspace，不决定 Sift 是否可以使用它。例如 `D:\Downloads\61850.pdf` 可以直接成为 Source。DSH 原生 Agent 文件工具能否直接访问这个路径，是 DSH Tool 的限制，不是 Sift 的业务限制。Sift 自己通过 Host / Tool 提供 Source 能力：

```text
Agent → Sift Source Tool → SourceResolver → external file
```

无需为了 AI 使用而强制复制文件进 Workspace。

### 2.3 不统一存储位置，只统一消费方式

Source 可以来自 Workspace 文件、本机外部文件、URL、粘贴生成的文件，不要求统一路径。统一的是：

```text
Source ID → SourceResolver → 读取 / 搜索 / 定位
```

### 2.4 Reference 必须持久化

Reference 不是长期知识资产，但它是 **Document 的可恢复工作现场**。因此创建 → 使用 → 关闭 DSH → 下次打开 → 恢复。只有用户主动移出时才删除。

### 2.5 一次只完成一个闭环

开发节奏：实现 → 运行 → 验证 → 测试 → 再进入下一阶段。禁止一次性重写整个仓库。

## 3. 三个核心技术接缝

v0.2 重点不是设计大量基础设施，真正需要钉死的只有三个接缝：

- **3.1 SourceResolver** —— 不同类型、不同位置的 Source 如何被统一读取。
- **3.2 ReferenceCodec** —— Reference 如何低摩擦进入原生 DSH Session。
- **3.3 DocumentChangeTool** —— AI 如何提出 Document 修改，而不是直接覆盖文件。

## 4. 推荐模块结构

```text
src/
├── shared/     source.ts / reference.ts / document.ts / workspace.ts
├── host/
│   ├── source/     resolver.ts / file-source.ts / url-source.ts / tools.ts
│   ├── reference/  store.ts
│   └── document/   store.ts / change-tool.ts
├── client/
│   ├── dsh-adapter/
│   ├── source/ reference/ document/ layout/
└── storage/    config-store.ts / source-store.ts / reference-store.ts / document-store.ts
```

目录名称可以调整，重点是依赖方向明确。

## 5. Workspace Profile

Sift 仍然依附 DSH Workspace。Workspace 本身不重新实现，只在 Workspace 内保存 `.sift/config.json`：

```json
{ "schemaVersion": 1, "profile": "sift" }
```

不要再增加 `version: "0.2"`。产品版本和数据 schema 版本分开。

## 6. Workspace 打开逻辑

进入 Workspace 时读取 `.sift/config.json`：不存在 → Default Workspace；存在 `{"profile":"sift"}` → 加载 Sift Layout。Default Workspace 不受影响。

## 7. DSH DOM 适配

Sift 当前需要修改 DSH Web 页面布局。这是现实约束，不需要假装不存在。但所有 DOM 假设必须集中：

```text
src/client/dsh-adapter/
├── selectors.ts
├── layout.ts
└── workspace-entry.ts
```

禁止业务组件自己到处 `document.querySelector(...)`。

- **7.1 当前版本支持**：第一版明确以 DSH `0.1.5-rc.2` 为目标版本。DSH 升级后重新跑适配验证，有问题修改 dsh-adapter。不为未知未来提前设计兼容框架。
- **7.2 最低失败处理**：如果关键 DOM 锚点不存在，不启用 Sift 三栏，并输出明确错误，不要继续重排页面导致半屏失效。

## 8. 三栏布局

```text
┌──────────────────┬──────────────────┬──────────────────┐
│ Reference Board  │ Document         │ DSH Session      │
└──────────────────┴──────────────────┴──────────────────┘
```

Source 不作为第四栏，通过 Drawer 临时进入。

## 9. Source 数据模型

```ts
type SourceType = 'file' | 'url'
type SourceLocation = 'workspace' | 'external'

interface Source {
  id: string
  type: SourceType
  title: string
  target: string
  location?: SourceLocation
  createdAt: string
}
```

## 10. Source 类型

- **10.1 Workspace 文件**：`type=file`、`location=workspace`、`target=` 相对路径，例如 `docs/fiber.md`。
- **10.2 本机外部文件**：`type=file`、`location=external`、`target=` 绝对路径，例如 `D:\Downloads\61850.pdf`。直接使用，不强制复制。
- **10.3 URL**：`type=url`、`target=https://...`。第一版只保留基本 URL Source 能力，网页正文抽取可后补。
- **10.4 粘贴创建文件**：粘贴内容 → 输入文件名 → 当前 Workspace 创建 md → 自动登记 Source。创建文件和添加 Source 是同一个操作。

## 11. SourceResolver

v0.2 的第一个核心基础设施。接口目标：

```ts
interface SourceResolver {
  getInfo(source: Source): Promise<SourceInfo>
  read(source: Source, options?: ReadOptions): Promise<SourceContent>
  search(source: Source, query: string): Promise<SearchResult[]>
}
```

第一版不要求所有 Source 都实现所有能力。

## 12. File Source

对于文本型文件（md、txt、ts、js、java、cs、json、yaml、xml…），优先实现 `read` 与 `search`。搜索先使用简单文本搜索。不要第一版上向量库、embedding、复杂索引。

## 13. PDF / DOCX 等 Source

已有 `material-preview.ts`、PDF.js、docx-preview 可以继续作为人的预览能力。AI 提取部分不要一开始就要求完美支持所有格式，可以逐步实现 Source reader。

## 14. Source Tools

给 DSH Agent 注册 Sift 自己的工具。第一版建议至少：

```text
sift_get_source_info
sift_read_source
sift_search_source
```

例如 `sift_read_source(sourceId, range?)`。Sift Host 根据 `sourceId` 找到真实资源。因此 Agent 不需要知道这个 Source 在 Workspace、`D:\Downloads` 还是其他地方。

## 15. 大 Source 的处理原则

第一版不做「把整个 100 万字 Source 塞进模型」，而是：

```text
搜索 → 定位 → 局部读取 → 候选 Reference
```

典型过程：用户说「找 Workspace 生命周期相关内容」；Agent 调 `sift_search_source` 拿到匹配位置，再调 `sift_read_source` 阅读局部，然后生成候选 Reference。这是 v0.2 的核心信息收紧机制。

## 16. Source Drawer

Reference Board 中 `+ 从来源获取` 打开 Source Drawer，包含已有 Sources 与 `+ 工作区文件`、`+ 本机文件`、`+ URL`、`+ 粘贴并创建 Markdown`，并支持选择多个 Source。

## 17. Reference 模型

```ts
interface Reference {
  id: string
  documentId: string
  content: string
  sourceId?: string
  locator?: string
  note?: string
  createdAt: string
}
```

Reference 只属于当前 Document。

## 18. Reference 持久化

建议 `.sift/references.json`：

```json
{
  "schemaVersion": 1,
  "documents": {
    "doc-1": [
      {
        "id": "ref-1",
        "content": "Workspace 与已有目录绑定……",
        "sourceId": "source-1",
        "locator": "L120-L150",
        "createdAt": "..."
      }
    ]
  }
}
```

Reference 的选中状态不需要持久化。需要恢复：内容、来源、locator、顺序。

## 19. Reference Board

一级直接展示内容，默认建议截断到 200～300 字，然后提供展开、查看来源、复制、移出。避免「整份 5 万字文件 → 5 万字 Reference Card」破坏工作台信息密度。

## 20. Source → Reference：基础路径

先做最简单的「短 Source → 整份加入 → Reference」。如果内容过长，提示「内容较长，建议让 AI 从 Source 中提取参考」，可以继续允许加入，但不要默认整张无限展开。

## 21. 粘贴 → Reference

支持 `+ 粘贴参考` 直接创建 `sourceId = undefined`，不需要为了数据模型强制先创建 Source。以后若希望长期保存，可「保存为 Workspace Markdown」。

## 22. AI 提取候选 Reference

流程：选择 Sources → 用户说明当前问题 → Agent 使用 Source Tools → 生成候选 → 用户确认 → Reference Board。

### 22.1 Candidate

候选不是长期数据对象，只是 UI 状态：

```ts
interface ReferenceCandidate {
  content: string
  sourceId?: string
  locator?: string
}
```

用户确认后才创建 Reference。

## 23. Reference → Session

这部分直接使用 DSH 官方 Input Trigger / Reference 机制，不再自己造 Prompt 注入协议。核心对象是 `ReferenceInsert` 与 `ReferenceCodec`。

## 24. ReferenceCodec

Sift 注册自己的 Reference 类型。用户输入 `@参考` 选择 `R1 R2 R3`，输入框出现 Reference Chip。提交时由 `ReferenceCodec.serialize()` 负责转成模型真正接收的内容。

### 24.1 serialize 内容

例如：

```text
[Sift Reference]

Source:
architecture.md

Locator:
L120-L150

Content:
Workspace 与已有目录绑定……
```

格式集中在 `ReferenceCodec.serialize`，UI 不自己拼 Prompt。

## 25. Reference Board → Input

除了原生 `@参考`，Reference Board 还提供「发送到对话」。作用只是把当前选中的 References 插入原生输入框 chips，**不直接发送**。用户仍然可以继续输入自己的问题，例如：

```text
[R1] [R2]

这两个描述是不是矛盾？
```

## 26. ReferenceCodec Spike

正式开发前期做一个很小的验证。硬编码 `R1 R2 R3`，实现「`@参考` → 插 chip → 发送 → serialize → 模型收到内容」。验证通过即可。这是技术确认，不是长期 Gate；完成后立即进入正常开发。执行记录见 [v0.2 阶段 0](v0.2-阶段0-技术验证.md)。

## 27. Document 模型

```ts
interface SiftDocument {
  id: string
  path: string | null
  title?: string
}
```

正文仍然是普通 Markdown 文件。

## 28. Untitled Document

创建 Sift Workspace 时默认创建 Untitled Document，但不立即写磁盘（`path = null`）。用户可以加 Source、加 Reference、对话、写内容。首次保存时再创建 Markdown。

## 29. Untitled 关闭

如果未保存，关闭时确认是否丢弃。丢弃则 Document state 删除、Reference 一起删除，不做 orphan。第一版不需要复杂恢复机制。

## 30. Document 删除语义

Sift 中「移除 Document」只代表从 Sift 工作状态中解除登记，默认**不删除 Markdown 文件**。未来若要提供真实文件删除，必须是单独明确操作。v0.2 不做。

## 31. Document 外部改名 / 移动

如果保存路径不存在，标记 `Document Missing`，提供「重新绑定文件」即可。第一版不自动跟踪 rename。

## 32. Document Editor

优先复用现有 `document-editor.ts`，保留已有 Markdown 编辑、保存、外部修改检测、冲突处理。不要重新实现编辑器。

## 33. Session → Document

AI 不直接覆盖 Document。Agent 如果需要修改当前 Document，调用 `sift_propose_document_change`。

## 34. DocumentChangeTool

```ts
sift_propose_document_change({ documentId, content, reason? })
```

返回后进入 `Current Document` vs `Proposed Document` 的 Diff。

## 35. 为什么使用 Tool

不要依赖「让 AI 输出 markdown code block → 客户端解析」，因为协议容易漂、文本容易混入解释、解析复杂。Tool 更明确：这是一次文档修改提案。

## 36. Diff

第一版只要求 Current vs Proposed 与 Accept / Reject。如果现有能力已经支持局部接受，继续复用；否则不要阻塞主链。

## 37. 局部批注

放到主链跑通后。流程：选中 Document 一段 → 写批注 → 发送 Session → Agent 调用 DocumentChangeTool → 新 Diff。不要单独建立复杂 Annotation 数据模型。

## 38. 数据存储

```text
workspace/
├── .sift/
│   ├── config.json
│   ├── sources.json
│   ├── documents.json
│   └── references.json
└── *.md
```

所有数据文件带 `schemaVersion`。

## 39. Store 实现

可以从现有 `src/host/materials.ts` 抽取已有成熟模式，继续保留串行写入、临时文件、rename 原子替换、损坏数据不静默覆盖、路径检查。不用重新发明 Store。

## 40. 多窗口

v0.2 不重点解决同一 Workspace 多窗口并发编辑 `.sift` 数据。目标场景是个人本地单工作区使用。保持原子写入即可，出现明确需求以后再加锁或版本控制。

## 41. 旧代码清理

- **可以立即删除**：已经不进入打包链的死代码——旧 workbench、旧 Solution / Project domain、未注册的 runtime transform / beforeSubmit、其他确定无引用模块。越早删越好。
- **暂时保留**：当前仍提供能力的 `materials-panel`、`material-preview`、`document-editor`、Host storage。等对应 v0.2 模块接管后再删。不要提前把还能用的实现全部清空。

## 42. 重点复用资产

- `src/host/materials.ts`：复用 Store 写入方式、文件处理方式。
- `document-editor.ts`：复用 Markdown 编辑、保存、冲突处理。
- `material-preview.ts`：复用 Markdown / PDF.js / docx-preview，以后作为 Source 查看能力。
- DSH Input Trigger：复用 `@` Reference、Reference Chip、ReferenceCodec。

## 43. 测试策略

分三层，不要求一开始引入完整浏览器自动化。

- **单元测试**：Source Store、Reference Store、Document Store、SourceResolver、`ReferenceCodec.serialize`。
- **集成测试**：真实 DSH Host、Tool 注册、Source Tool、Document Change Tool。
- **人工主链验收**：创建 Sift Workspace → 添加 Source → Source → Reference → Reference → Session → AI → Document Proposal → Accept → 关闭 → 重启 → 恢复。以后觉得维护成本上升，再引入 Playwright。

## 44. Phase 0：技术钉点 + 清死代码

目标：先确认关键接缝。工作：删除确定死代码、验证 DSH Workspace Profile 注入、做 ReferenceCodec spike、做 DocumentChangeTool 最小 tool spike。

验收：`@参考` chip 能送到模型；Agent 能调用一个假 document change tool。

→ 执行记录：[v0.2 阶段 0](v0.2-阶段0-技术验证.md)

## 45. Phase 1：v0.2 骨架

实现 Sift Workspace Profile、三栏布局、dsh-adapter、Untitled Document。此时 Reference 空、Document 可编辑、Session 原生可用。验收：Default Workspace 不受影响。

## 46. Phase 2：Source 基础

实现 Source Store、Workspace 文件 Source、External 文件 Source、URL Source、粘贴创建 Markdown Source、Source Drawer。验收：重启后 Source 恢复。

## 47. Phase 3：SourceResolver

实现文本文件 read、文本文件 search、workspace / external 统一调用。先不追求所有格式。验收：同一 API 能读取 workspace md 与 external txt。

## 48. Phase 4：Reference 基础

实现 Reference Store、Reference Board、整份短 Source → Reference、粘贴 → Reference、移出、展开、查看来源。验收：切换 Document 时 Reference Board 正确切换；重启后 Reference 恢复。

## 49. Phase 5：Reference → Session

正式接入 ReferenceCodec、`@参考`、Reference Board → 插入 chips。验收：用户勾选 R1 R2 → 发送到对话 → 继续输入问题 → 发送，模型正确拿到 Reference 内容。

## 50. Phase 6：Source Tools

注册 `sift_get_source_info`、`sift_read_source`、`sift_search_source`，支持 Agent 操作 workspace Source 与 external Source。验收：Agent 不需要知道真实路径类型，只使用 `sourceId`。

## 51. Phase 7：AI 提取 Reference

实现「选择 Sources → 告诉 AI 当前问题 → Agent search / read → 生成 Candidate → 用户确认 → Reference」。这是 v0.2 真正验证 Source → Reference 价值的阶段。验收：从多个中大型文本 Source 中能快速得到少量有效 Reference。

## 52. Phase 8：DocumentChangeTool + Diff

实现 `sift_propose_document_change` → Proposed Document → Diff → Accept / Reject。验收：Reference → Session → AI 修改建议 → Document 完整闭环成立。

## 53. Phase 9：体验收口

再处理 Reference 卡片长度、栏宽保存、Source 查看、Document 切换、错误提示、文件失效重绑。不要在前面阻塞主链。

## 54. Phase 10：删除旧 Materials 主链

确认 v0.2 可用后，删除旧 Material workflow、旧 Materials Panel 状态、旧素材关系、旧重复 UI。预览组件等通用能力继续保留。

## 55. 开发顺序

```text
0. DSH 接缝 spike
   ↓ 1. Workspace Profile + 三栏
   ↓ 2. Source
   ↓ 3. SourceResolver
   ↓ 4. Reference Board + 持久化
   ↓ 5. ReferenceCodec
   ↓ 6. Source Tools
   ↓ 7. AI 提取 Reference
   ↓ 8. DocumentChangeTool + Diff
   ↓ 9. 体验完善
   ↓ 10. 删除旧主链
```

## 56. 真正需要验证的三个点

- **A. Source → Reference**：重点不是「AI 能不能总结」，而是「用户能不能从很多信息里很快拿到当前真正需要的几条内容」。这是 Sift 最大的产品验证。
- **B. Reference → Session**：已有 DSH 官方通道，主要验证手感是否足够低摩擦。
- **C. Session → Document**：重点验证 AI 修改能不能顺畅进入正式笔记，同时用户始终掌握最终修改权。

## 57. v0.2 不做

Solution、Project、Task；全局 Reference Library、Reference 标签、知识图谱、无限白板；复杂权限体系；Source 强制搬入 Workspace；向量数据库、Embedding 检索；自研 PDF 阅读器、自研 DOCX 阅读器；复杂多窗口同步；自动 Document rename tracking；完整浏览器 E2E 基础设施。

## 58. v0.2 完成标准

用户能够：创建 Sift Workspace → 添加 Workspace 文件 / 本机外部文件 / URL / 粘贴生成文件 → 从 Source 找信息 → 形成 Reference → Reference Board 恢复工作现场 → 选 Reference 插入 DSH Session → 与 AI 分析 → AI 提出 Document 修改 → Diff → 接受 → 关闭 DSH → 第二天重新打开 → 继续昨天的 Document + Reference。

这条链顺畅，v0.2 完成。

## 59. 最终技术结构

```text
                   Sift Workspace
                         │
                  Source Store
                         │
                  SourceResolver
                         │
             ┌───────────┴───────────┐
             │                       │
           用户                     Agent
             │                       │
             │                 Source Tools
             │                       │
             └───────────┬───────────┘
                         ↓
                  Reference Board
                         │
                  ReferenceCodec
                         │
                    DSH Session
                         │
                DocumentChangeTool
                         │
                      Diff
                         │
                    Document
```

这里没有第二套 Agent，也没有第二套文件系统。Sift 只负责把原始来源、当前参考、AI 对话、正式产出四者接起来。

## 60. 实施结论

v0.2 的技术重点不应该继续扩散。只需要把三件事做好：

- **SourceResolver** —— 信息怎么进来并被读取。
- **ReferenceCodec** —— 当前参考怎么进入 AI。
- **DocumentChangeTool** —— AI 的结果怎么进入正式文档。

剩下的 Source Drawer、Reference Board、Document Editor 都只是围绕这三个接缝提供低摩擦交互。因此实施原则最终可以压成一句：

> **入口保持开放，工作状态保持简单，DSH 能复用的全部复用，只在 Source、Reference、Document 三个边界上增加 Sift 自己真正需要的能力。**
