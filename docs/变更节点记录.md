# 变更节点记录

本文记录 Sift 在产品目标、核心对象和使用流程上的几次重要变化。日期对应方向被明确或主要实现落地的时间，不替代完整的 Git 提交历史。

## 2026-09-10：从自动总结转向人的知识梳理

Sift 最早要解决的问题是：怎样把低密度、零散、甚至相互矛盾的材料，逐步整理成用户真正认可的 Markdown 笔记。AI 负责搜索、比较和提出修改，人决定方向、事实是否成立以及最终保留什么。Sift 不用掌握度或完成度算法评价用户。

当时采用了一套偏管理型的模型：

```text
解决方案
└── 项目
    ├── 素材
    ├── 会话
    └── 成果笔记
```

这套模型能表达素材共享、项目会话和笔记写回，但也让 Sift 越来越像一套知识项目管理系统。

## 2026-09-11：三栏项目工作台成形

第一版完整工作台围绕“边看材料、边写笔记、边和 AI 讨论”展开。界面已经呈现出后来一直保留的三栏结构：

```text
素材 ｜ 产出 ｜ 原生 DSH 对话
```

这一阶段实现了素材阅读、项目会话、选区批注、发送记录、受限笔记写回和工作现场恢复，也验证了一个重要边界：右栏应直接复用 DSH 的消息流、输入框和模型能力，Sift 不维护第二套会话系统。

问题也逐渐显现。Solution、Project、Material 和 Annotation 形成了一套较重的领域模型，很多开发工作落在管理对象和兼容状态上，离“整理一篇笔记”的直接流程越来越远。

## 2026-09-14：放弃顶层项目系统，融入 DSH Workspace

Sift 开始收缩通用工作台和项目管理抽象。一级入口改为 DSH Workspace，Sift 只作为一种工作区类型存在：

```text
DSH Workspace
├── profile = default
└── profile = sift
```

Workspace、Session、模型和 Agent 生命周期继续由 DSH 管理。Sift 只处理工作区中的材料上下文和 Markdown 产出。这个变化删除了第二套顶层导航，也明确了普通 DSH 工作区不能受到 Sift 影响。

## 2026-09-15 至 09-16：从素材预览转向信息收紧

早期左栏的重点是文件与网页预览，支持 Markdown、PDF、DOCX 和 URL。实际设计过程中逐渐确认，预览文件只是基础能力，Sift 真正要解决的是信息量的逐层收紧：

```text
大量原始信息
    ↓
当前真正有用的信息
    ↓
自己长期保留的内容
```

由此形成四个对象：

- Source 是稳定可访问的原始信息。
- Reference 是当前思考和写作正在使用的内容。
- Document 是长期维护的 Markdown 产出。
- Session 复用 DSH，负责人与 AI 的中间加工。

产品目标被概括为：

```text
Source → Reference → Session → Document
```

旧 Solution、Project、Material 和复杂 Annotation 主链退出。Source 与 Document 是长期资产，Reference 是可以恢复的工作现场。

## 随后：Reference 成为正式对象

Reference 不再是左栏里临时堆放的剪贴内容。实现逐步确定为：一个 Reference 对应一个 JSON 文件，内部包含多张 Card；Card 保存正文以及可选的网页或本机文件来源。

Reference Card 先后具备粘贴识别、编辑、删除、拖动排序和 History。这样做以后，Reference 成为一个明确的材料组织单位，可以独立保存和继续整理。

界面也从管理表单转向直接操作。早期入口更接近 CRUD：

```text
Reference Board
当前参考
添加参考
```

后来改成类似编辑器的 Tab：

```text
[参考 A] [参考 B]                 添加已有  编辑  新建
```

Tab 只负责切换工作对象，下面直接展示和操作 Card。新建 Reference、添加已有 Reference、关闭 Tab 和永久删除文件也开始拥有各自的入口。

## 2026-09-20：从单一 Document 扩展为多个 Output

中栏最初一次只处理一篇 Markdown，随后引入 Output Tabs，使同一个 Workspace 可以同时维护多篇产出：

```text
[设计.md] [总结.md]               添加已有  编辑  新建
```

一次仍然只编辑一个 Output，但用户可以新建 Markdown、添加已有文件、切换、重命名、从工作区移除或永久删除。Output 的内容继续使用 Milkdown 编辑并自动保存。

代码和界面中一度同时使用 Document 与 Output 两个名称。它们在当前工作流中指向同一类对象：用户准备长期保留的 Markdown 文件；Output 更强调工作区里的 Tab 和操作状态，Document 更强调产品模型中的正式产出。

## 2026-09-20：Output 带着自己的 Reference 上下文

多个 Output 出现后，Reference 不能继续作为一份全局列表。关系模型收敛为：

```text
Output A → Reference A、B
Output B → Reference B、C
```

切换 Output 时，左侧只恢复它关联的 Reference Tabs。没有活动 Output 时，Reference 仍然可以作为自由工作集独立整理。新建 Output 会继承创建前可见的 References；添加已有 Output 只在尚未建立关系时初始化，不覆盖已有关系或明确的空关系。

到这里，三栏各自的职责已经稳定：

```text
Reference              Document / Output          Conversation
当前材料上下文           长期 Markdown 产出          原生 DSH 会话
```

## 2026-09-20：拆开创建、选择、关联和切换

Reference / Output 联动中最重要的一次收敛，是把四类动作彻底分开：

```text
创建       新建 Reference 或 Output 文件
选择已有   把已有文件加入当前工作集
关联       明确保存 Output 与 References 的关系
切换       根据已有关系恢复工作上下文
```

由此形成几条必须保持的规则：

```text
创建文件 != 打开文件
打开文件 != 建立关联
切换文件 != 修改关联
关闭 Tab != 删除物理文件
```

关系单独保存在 `relations.json`，Reference 和 Markdown 文件不需要感知自己被谁使用。UI 的职责主要是切换当前工作对象、展示关系结果，并为有副作用的操作提供明确入口。

## 2026-09-21：重新划定 AI 交互的边界

Sift 曾加入“选中文字 → 写下本轮想法 → 随下一轮消息发送”的交互。它可以把 Reference 或 Document 中的具体选区送入 DSH 原生输入框，但这种模式与成熟 AI 客户端的选区批注高度重叠。

因此，批注界面本身不再被视为 Sift 的核心能力。后续只保留工作材料进入原生 Session 所需的薄适配，不继续发展第二套聊天、复杂批注历史或独立发送协议。

当前方向已经收敛为一个本地文件工作环境：以 Document 为长期产出，以 Reference 维护当前材料上下文，以 Conversation 辅助分析和修改。下一步仍要补齐的是 Source 到 Reference 的筛选，以及 AI 修改进入 Document 前的 Diff 审查。
