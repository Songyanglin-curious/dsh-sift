## 2. 接缝一：ReferenceCodec

**要解决的问题**：Reference 如何低摩擦进入原生 DSH Session。

实现：

| 文件 | 职责 |
| --- | --- |
| `src/client/dsh-adapter/input-trigger.ts` | 唯一集中复刻 DSH `@` 触发源契约的地方（含注册与释放） |
| `src/client/reference/codec.ts` | 纯函数：`clipboardText` 与送给模型的 `[Sift Reference]` 正文 |
| `src/client/reference/source.ts` | 把「参考记录读取器」包装成 `@` 触发源 |
| `src/client/index.tsx` | 注册 source；Phase 0 传入硬编码的 `SPIKE_RECORDS`（R1/R2/R3） |

关键结论（均有 path:line 依据，见 [DSH 自定义 @reference 类型 API 调研](dsh-reference-api-research.md)）：

- 注册入口是 **`ctx.inputTriggers.registerSource(source)`**，服务名不是包名；client 半的 `inject` 里必须写 `'inputTriggers'`。
- `codec.serialize(ref, signal)` 的返回值会**替换 chip 在草稿里的区间**，拼成发给模型的 **user message 正文**。它不是 attachment，也不是 tool result。
- **serialize 抛错会阻断整次发送**，契约明确不允许静默退回 `clipboardText`——所以找不到参考时必须抛错，这一点已写进实现并有测试覆盖。
- `clipboardText` 会被 DSH 持久化进草稿，且 `U+FFFC`、`U+E100–U+E11D` 会被占位符剥离，因此正文投影必须避开这些码位。

Phase 5 接入真正的 Reference Board 时，只需把 `createSiftReferenceSource` 的读取器从 `SPIKE_RECORDS` 换成 Reference Store，上述三个文件不需要改动。

## 3. 接缝二：DocumentChangeTool

**要解决的问题**：AI 如何提出 Document 修改，而不是直接覆盖文件。

实现：

| 文件 | 职责 |
| --- | --- |
| `src/host/tools/contract.ts` | 注册工具所需的最小契约复刻 |
| `src/host/document/change-tool.ts` | `sift_propose_document_change` 定义 + 内存提案存储 |
| `src/host/index.ts` | `static inject` 增加 `'tools'`，构造时注册工具 |

两条容易写错的硬约束（直接核对 `dsh-tools/lib/index.js` 后确认）：

- 手搓 `ToolDefinition` 时，`output.schema` 必须用**标准 `required: string[]`**。注册表对它跑 `assertSupportedJsonSchema`，而受支持子集里**没有**属性级 `required: true`（那是 `defineTool` 的 DSL 写法，由编译器在 `lib/index.js:846` 提升为 `required: string[]`）。
- `parameters` 同样必须是 **raw JSON Schema**：注册时完全不校验，但下游（`jsonSchemaToTs`、`renderType`）直接消费 raw JSON Schema。

提案目前只存在内存里（每个 Document 保留最新一条，`peek`/`take` 语义），客户端读取通道到 Phase 8 再接。

## 4. 验证

### 自动检查

- `pnpm test`：**60 个测试全部通过**（9 个文件）。新增 `tests/reference-source.test.ts`（13）与 `tests/document-change-tool.test.ts`（10）。
- `tsc --noEmit`：通过。`node scripts/build.mjs`：通过。
- `tests/document-change-tool.test.ts` 内置一个镜像注册表 `assertSupportedJsonSchema` 的校验器，防止写出注册表不接受的 `output.schema`。

删除前记录到的基线：`tests/materials-workspace.test.ts` 在冷启动下有 4 个超时失败；删除后复跑全部通过，确认那是首次运行的耗时抖动，不是被删代码引起的。

### 真实 DSH 运行时

开发 Home 的探针插件新增 `GET /sift`（`scripts/runtime/probe.mjs`），用于读取宿主侧接缝的真实状态。在隔离实例（`SIFT_DEV_PORT=9182`）上得到：

```json
{ "hasToolsService": true, "hasSiftService": true, "toolCount": 1,
  "siftTools": ["sift_propose_document_change"] }
```

三点意义：

1. `hasSiftService: true` —— 宿主插件在 `inject = ['workspaceRegistry', 'tools']` 下**成功加载**，说明 `tools` 可注入。
2. `siftTools` 含 `sift_propose_document_change` —— 工具**真的进了 DSH 注册表**。
3. 注册成功本身即证明手搓的 `output.schema` **通过了注册表的真实 `assertSupportedJsonSchema`**，不只是本地测试的镜像校验。

客户端侧：从运行中的实例拉取 `/plugins/??@songyanglin/dsh-sift/client.js`（10.4 MB），确认其中包含 `inputTriggers`、`registerSource`、`[Sift Reference]` 与 `@参考:` 投影，即浏览器实际加载的产物带着这个 spike。

## 5. 未验证 / 待人工确认

- **浏览器内的 chip 行为**：`@参考` 菜单能否列出 R1/R2/R3、选中后是否出现 chip、提交后模型是否真的收到 `[Sift Reference]` 正文。探针只能看到 bundle 与宿主注册表，看不到 Lexical 编辑器状态，需要在页面里人工过一遍。
- **Client 的 `inject` 闸门**：`'inputTriggers'` 已确认是正确服务名、且 `ui-input-trigger` 在 web profile 中被挂载；但 `apply` 是否真的被调用仍需在页面里确认（若服务名写错，`apply` 会静默不执行）。
- `detect`/`draftRev` 的 span 数学：Phase 0 未使用（只能通过 `@` 菜单插入 chip），Reference Board 的「发送到对话」按钮会用到，见调研报告 §5.1 与 Unknowns 第 1 条。
