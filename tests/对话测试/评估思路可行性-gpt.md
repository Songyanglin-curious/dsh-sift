Sift 是一个面向个人知识工作的本地 AI 工作台。它不以对话为中心，而是把当前参考材料（Reference）、正在推进的文档（Target）和 AI 对话（Conversation）放在同一个工作现场中，让用户把注意力更多放在“正在参考什么、正在形成什么”，而不是长期维护一场越来越复杂的聊天。Reference 可以来自网页、AI 对话、本地文件或临时粘贴内容，真正需要长期保留的结果最终收敛到 Document。

Sift 最初的设想更偏向于**批量处理大量素材**：把分散在 GPT、Codex、Trae、网页和本地文件中的信息统一收集，再借助 AI 整理、提炼并形成笔记。

实际探索后遇到了一个核心问题：**AI 的信息处理和生成速度远远高于人的吸收速度。**

AI 可以非常容易地把几十场对话批量总结成几十份材料，但这些加工结果仍然需要人重新阅读、判断和理解。更麻烦的是，AI 生成内容的信息密度往往并不高，甚至可能产生比原始素材更多的文字。结果是自动化虽然提高了“产出量”，却同时制造了新的阅读负担和认知债务。

完全依赖人工选择 Reference 也存在另一面的问题。虽然 Sift 已经尽量降低了输入摩擦，例如文本和网页内容可以直接粘贴生成带来源的 Reference，但“哪些内容值得留下、哪些属于同一问题、哪些应该进入当前工作”仍然需要人持续判断。

因此目前的问题逐渐从“如何让 AI 批量生成整理结果”转变成：

**能不能在不制造大量新内容的情况下，先帮助人把复杂的原始素材整理成更容易理解和选择的结构。**

“以问题为抓手整理 AI 会话”就是在这个背景下出现的一条新思路。

---

Sift 最初希望能够批量处理大量 AI 会话，但逐渐发现，真正的瓶颈不是 AI 的处理能力，而是人的认知带宽。AI 可以快速生成摘要、整理稿和知识卡片，但这些新产物仍然需要人重新阅读和判断，甚至可能因为信息密度下降而增加负担。

因此可以换一个方向：**不让 AI 批量生产新的内容，而是批量整理原有会话的结构。**

AI 会话天然由一轮轮 User / Assistant Turn 组成。物理上的最小单元可以定义为“一问一答”，但实际分析时不能完全脱离上下文，因为用户经常会说“对”“不是这个”“那前面那个呢”等依赖上文的话。

这里比较关键的观察是：**多数 AI 会话中，真正推动讨论方向变化的是用户的问题，而 Assistant 的回答主要负责展开。** 用户输入通常更短、信息密度更高，并且连续问题之间往往具有很强的逻辑关联。

因此可以采用“Question-first”的处理方式：

```text
完整会话
→ 拆成 Q/A Turn
→ 以 User Turn 为主要语义骨架
→ 判断问题之间的继续、切换、回归关系
→ 将散落在会话中的相关 Turn 重组为 Discussion Thread
→ 用户选择其中有价值的 Thread 加入 Sift Reference

```

例如原始会话可能是：

```text
Sift定位 → Reference问题 → UI问题
→ 回到Reference → 认知带宽
→ 插入其他问题 → 再回到认知带宽

```

处理后可以形成几条相对连续的讨论线：

```text
Sift / Reference设计
Q3 → Q4 → Q7

Sift / 认知带宽
Q8 → Q9 → Q13

Sift / UI交互
Q5 → Q6

```

Thread 中仍然保留原始 Assistant 回答，需要时再展开。系统原则上不生成新的摘要或“知识”，主要处理**关系、顺序和分组**。

这种方式的价值在于：原本需要人在几百轮聊天中反复翻找，现在可以先压缩成十几条候选讨论线，再选择真正需要进入当前工作的部分。

它也更符合 Sift 现在的定位：

**批量处理关系，而不是批量生产内容。**

目前最大的未知点不是技术实现，而是“问题之间的关系到底能识别到什么程度”。同一组问题究竟是一条连续推演，还是几个独立主题，本身存在主观性。因此 AI 更适合作为初步整理器，提供可修改的结构；用户仍然需要能够方便地 Merge、Split、移动和删除。

这条路线值得继续讨论，因为它没有试图突破人的认知带宽，而是在进入认知阶段之前，先把复杂会话的结构整理干净。

整体可行，而且相比“批量总结 AI 会话”，这条路线和 Sift 的定位更一致。但它成立的前提不是 **AI 能把 Thread 分得多准**，而是 **AI 分错以后，人修正结构的成本足够低**。

| 维度 | 正面判断 | 反面判断 |
|---|---|---|
| 产品逻辑 | 很成立。它减少的是“浏览复杂度”，没有额外制造一层知识产物 | 如果整理后的 Thread 仍然需要逐条重新阅读，收益会迅速下降 |
| 信息损失 | 比摘要小很多，原始 Q/A 仍然存在，结构只是视图 | 分组本身也是一种解释，错误分组可能制造错误认知 |
| AI 适配度 | 主题延续、切换、回归这类关系判断，LLM 很适合做初筛 | 精确判断“是不是同一问题”具有明显主观性，不可能完全自动化 |
| Question-first | 用户问题确实通常更接近“意图骨架”，token 也少，处理成本低 | 不能变成 User-only；“对”“继续”“不是这个”完全依赖 Assistant 和前文 |
| Sift 契合度 | 非常高。最终仍是“选择 → Reference → Document”，不会出现新的知识体系 | 如果继续加入标签、摘要、自动命名、知识图谱，很容易重新膨胀成另一个知识管理系统 |
| 技术复杂度 | 中等，真正困难的不是模型调用，而是结构编辑和状态维护 | Merge / Split / Move / 回归 / 跨 Thread 等交互做不好，比普通聊天列表还难用 |

我认为这里有一个很重要的概念转变：

> **以前是在压缩内容，现在是在压缩导航空间。**

例如 300 轮聊天，不需要把它总结成 10 篇文章。只需要让用户先看到：

```text
Reference 设计        17 turns
认知带宽问题          12 turns
Sift 定位演化          21 turns
UI / 工作区设计         8 turns
无关讨论               34 turns
```

用户真正关心哪条，再展开原文。

这种压缩非常有价值，因为**它不会要求用户相信 AI 重新生成的东西，只要求用户借助 AI 更快找到原来的东西。** 这是这条路线最强的一点。

不过我会修正现在的一个表述：不是严格的 **Question-first**，而应该是 **User-turn-first，Context-aware**。

AI 可以主要看 User Turn 建立骨架，但判断时至少需要附近的 Assistant 回答。例如：

```text
Q8  我感觉这里问题不是 Reference
A8  ...
Q9  对，就是这个
```

单看 Q9 没有任何意义。

甚至还会出现：

```text
Q10  第一种不错，不过第二个问题……
```

一个 User Turn 本身就同时承担“承接上一条 + 开启新问题”。

所以比较稳妥的模型是：

```text
User Turn = Anchor
附近 Q/A = Context
Thread = AI 推测出的关系结构
```

而不是：

```text
User Turn = 完整语义单元
```

另外还有一个容易被低估的问题：**Thread 未必天然是互斥分类。**

一段讨论可能同时属于：

```text
Sift / Reference
Sift / 认知带宽
```

如果强迫 AI “每个 Turn 只能属于一个 Thread”，很快就会遇到边界问题。早期甚至不用解决复杂的多归属，可以允许用户把一个 Turn“复制引用”到另一个 Thread，而不是设计复杂知识图谱。

### 我认为真正决定成败的是三个指标

不是分类准确率。

**第一是压缩率。**

300 个 Turn 最终是不是能让我只面对 10～20 个候选 Thread。

**第二是修正成本。**

AI 把 Q7 放错地方，我能不能一次拖拽解决，而不是重新让 AI 分析。

**第三是回到原文的速度。**

看到一个 Thread 后，能不能立即展开原始 Q/A、定位上下文、选中几轮加入 Reference。

如果这三个成立，即使 AI 只有 80% 的结构判断正确率，产品都可能很好用。

反过来，即使模型能做到 95%，但用户还得大量检查、确认、维护标签，它仍然会成为新的认知负担。

所以我的评价是：**方向本身可行性较高，甚至比 Sift 最初的“素材批处理”方向更扎实；但应该把它定义成“会话导航与筛选工具”，而不是“自动知识整理工具”。**

最值得警惕的不是 AI 能不能识别 Thread，而是做着做着又开始加入摘要、标签、知识卡片、关系图、自动文档……最后重新制造一层需要用户管理的信息。

如果保持现在这句话——**“批量处理关系，而不是批量生产内容”**——我认为这条线值得做一个非常小的原型验证。

我觉得关键不是“给每个问答组算一个语义相似度”，而是要把 **直接相关** 和 **顺序承接** 分开算，最后再合起来。

最简单可以这样建模：

```text
Q1 → Q2 → Q3 → Q4 → Q5 → ... → Qn
```

每个 Q/A Group 都有两种关系：

```text
1. 它和当前目标有多相关
2. 它和前后问答有多连续
```

比如我们拿 Q20 当锚点：

```text
Q17  直接相关：高
Q18  直接相关：低
Q19  直接相关：低
Q20  锚点
Q21  直接相关：低，但明显是在承接 Q20
Q22  直接相关：中，继续 Q21
Q23  换话题
...
Q41  直接相关：高   ← 后面又回来了
```

如果只做语义相似度，Q21 很可能被漏掉；如果只依赖顺序，又会把 Q23、Q24 一路带进去。

所以我倾向于做两层。

第一层让 AI 判断**相邻关系**：

```text
Q18 ↔ Q19：强承接
Q19 ↔ Q20：强承接
Q20 ↔ Q21：强承接
Q21 ↔ Q22：普通相关
Q22 ↔ Q23：明显切换
```

这相当于知道“讨论惯性”在哪里断掉。

第二层才判断**当前主题 / 当前锚点与每一组的直接关联**：

```text
目标：“Sift 的认知带宽问题”

Q3   强相关
Q4   强相关
Q5   中等
Q17  无关
Q20  强相关
Q21  弱相关
Q41  强相关
```

然后做一个很轻的传播：

```text
最终相关度
≈ 直接相关度
+ 邻居相关度 × 相邻承接强度 × 衰减
```

这样 Q21 即使自身表达只是：

> “对，所以这里其实还是人的问题。”

单独看几乎没意义，但因为 Q20 高相关，并且 Q20→Q21 是强承接，它就会被带起来。

```text
Q22 → Q23 = 明显换话题
```

就停止。

远处的 Q41 则不是靠 Q20 一路传播过去，而是因为 **Q41 本身重新与目标高度相关**，所以再次亮起来。

```text
━━━━━━ 相关讨论 A ━━━━━

━━━━━━ 相关讨论 B ━━━━━
```

而不是硬说：

```text
Q3 ～ Q41 全是一个连续 Thread
```

我觉得这一点非常重要。

至于 AI 实际判断时，每个 Group 也不要完全孤立喂进去。可以让它看到一个很小的滑动窗口：

```text
Q(i-1) / A(i-1)
Q(i)   / A(i)
Q(i+1) / A(i+1)
```

或者至少：

```text

```

这样既保留上下文，又不至于把整场对话当成一个整体。

> **直接关联负责“发现”，顺序关联负责“补全”。**

前者能发现“隔了几十轮又回到这个问题”，后者能补上“对、继续、那这个呢”这种离开上下文就无法理解的内容。

```text
直接相关：0 / 1 / 2 / 3
前序承接：0 / 1 / 2 / 3
```

程序只负责非常简单的衰减传播和着色就够了。

我觉得这已经是一个比较能落地的骨架了。


需要理解上下文时再展开完整 Q/A。

目标是减少 AI 长回答对浏览空间的占用。

---

## 四、关联分析能力

关联分析不由传统程序算法完成，核心语义判断交给 AI。

程序只负责：

- 组织 Q/A 数据
- 提供适量上下文
- 调用 AI
- 接收结构化分析结果
- 缓存结果
- 显示颜色和导航

第一阶段支持两种分析入口。

### 1. 按主题分析

用户输入一个主题，例如：

```text
“人的认知带宽”
```

AI 判断整场会话中哪些 Q/A 与该主题相关。

### 2. 按 Q/A Group 分析

用户选择某个 Q/A Group：

```text
Q23
```

AI 判断整场会话中还有哪些内容与 Q23 存在语义关联、承接或回归关系。

---

## 五、关联分析原则

对话不能完全割裂分析，但也不能默认整场会话属于同一个上下文。

因此 AI 分析时采用：

```text
当前 Q/A
+
有限的前后上下文
```

具体上下文窗口大小后续实验确定。

AI 返回结果优先采用有限等级，而不是伪精确数值，例如：

```text
强相关
相关
弱相关
无关
```

必要时内部可以保留 score，用于排序和颜色映射，但 UI 不强调“87.3%”这类精确度。

暂不要求 AI 自动生成 Thread。

核心原则：

**AI 负责提示关系，人负责理解结构。**

---

## 六、关联结果展示

关联结果主要通过视觉方式呈现，而不是重新生成总结。

计划包括：

### Q/A 着色

根据关联程度改变 Q/A Group 的背景或边缘颜色深浅。

例如：

```text
Q12  ░
Q13  ██
Q14  ████
Q15  █
...
```

### 导航条

在会话侧边提供整体关联分布：

```text
│
│ ░
│ ███
│
│ █████
│
│ ██
│
```

用户可以直接点击高相关区域跳转。

目标是让用户快速看到：

- 第一次讨论出现在哪里
- 中间何时换题
- 后续哪里重新回到了这个问题

---

## 七、Reference 的生成

最终判断仍由用户完成。

关联分析不会自动生成 Reference。

支持两种主要方式：

### 文本片段

用户选择一段文字：

```text
选中文字
→ 添加 Reference
```

### Q/A Group

用户直接选择完整问答：

```text
Q/A Group
→ 添加 Reference
```

Reference 尽量保留来源信息，例如：

```text
来源 Conversation A
Q/A Group 23
原始内容位置
```

来源关系如果未来失效，不影响已经形成的 Document。

---

## 八、第一阶段暂不做

为了控制复杂度，以下功能暂缓：

- 自动生成 Discussion Thread
- 跨会话自动聚类
- 自动总结大量会话
- 自动知识卡片
- 知识图谱
- 多层级主题体系
- 强一致 Reference 关系
- 复杂长期知识库
- AI 自动决定哪些内容进入 Document

这些能力只有在实际使用明确出现需求后再考虑。

---

## 九、后续执行顺序

### Phase 1：会话基础视图

完成：

```text
会话导入
→ Q/A 拆分
→ 折叠 / 展开
→ User Turn 快速浏览
```

先验证长会话浏览体验。

### Phase 2：Reference 操作

完成：

```text
文本选择 → Reference
Q/A Group → Reference
Reference → 回到来源
```

形成最基础的 Source → Reference 流程。

### Phase 3：AI 关联分析实验

先只实现：

```text
指定 Q/A
→ AI 分析整场会话
→ 返回相关程度
```

使用真实长会话测试。

重点验证：

- AI 是否能识别跨段回归
- 短 User Turn 是否能结合上下文理解
- 多大上下文窗口比较合适
- 分批分析是否会出现明显漂移
- 调用成本和等待时间是否可接受

### Phase 4：关联可视化

加入：

```text
相关度着色
+
侧边导航条
+
快速跳转
```

验证关联分析是否真的降低翻找成本。

### Phase 5：主题关联分析

在 Q/A 锚点模式稳定后，再加入：

```text
输入主题
→ 扫描当前会话
→ 显示关联分布
```

### Phase 6：Document 工作流整合

最后把：

```text
Source
Reference
Document
```

真正串起来。

Reference 位于 Document 左侧，作为当前写作过程中的动态材料区。

---

## 十、当前最重要的验证问题

第一阶段不要验证“Sift 能不能理解整个知识体系”。

只验证一个非常具体的问题：

> **面对一场很长、讨论过多个问题、并且经常发生话题回归的 AI 会话，Sift 能不能让用户更快找到真正需要的那几段内容？**

如果答案是肯定的，再继续扩展。

如果关联分析最终仍然需要用户逐条检查所有内容，则说明这条路线价值有限，应及时停止继续增加复杂度。

---

## 当前核心原则

```text
不批量制造新内容。
优先整理原始信息的可见性和关系。

AI 提示，人做决定。

Reference 服务于当前工作。
Document 才是最终资产。

核心产物强保证。
工作关系尽力保证。
```

这份可以直接作为下一版设计基线，后面真正需要重点继续讨论的就是 **“AI 关联分析一次到底怎么喂上下文、怎么分批、返回什么结构”**。
